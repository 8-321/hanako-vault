**Codex**

kel，我做了只读审查，没有修改文件。结论先放前面：当前“灵枢”作为静态展示型 MVP 是成立的，但作为“中文 AI Skill 中枢 / 直接导入 / 发布 Skill / AI 自动整理”的产品承诺，最容易失败在“承诺超过实现”。真实用户一旦点发布、导入、下载、上传，就会发现很多动作只是提示或模拟。

**最可能失败点**

1. **“发布 Skill”是最大穿帮点**
红队攻击：文档承诺“粘贴内容，AI 自动整理”“发布到 Skill 库”，页面也写“上传 zip/html/SKILL.md/GitHub 链接”，但实现里只是 `processPublish()` 做正则提取，`confirmPublish()` 只弹“已发布”提示，没有保存、审核、入库、上传、后端或 PR 流程。用户会以为发布成功，实际什么都没进入库。
证据：[README.md](D:/Hanako/灵枢/README.md:23)、[小白对接文档.md](D:/Hanako/灵枢/小白对接文档.md:214)、[index.html](D:/Hanako/灵枢/src/index.html:134)、[app.js](D:/Hanako/灵枢/src/js/app.js:535)
蓝队修复：短期把文案降级为“整理预览 / 生成提交稿”，不要叫“发布”。中期做一个真实提交通道：生成 JSON 草稿、复制给维护者、或提交 GitHub Issue/PR。上线前必须有“发布后在哪里看见”的闭环。

2. **“一键导入”不是真的导入**
红队攻击：大多数 Skill 的导入只是复制一段简介、输入、输出、示例，并不是完整 `SKILL.md`、不是平台可识别包，也没有 Hanako / Claude / ChatGPT 的具体导入格式。`zip` 类型甚至只是 toast 提示“已准备好”，没有文件下载。
证据：[README.md](D:/Hanako/灵枢/README.md:22)、[app.js](D:/Hanako/灵枢/src/js/app.js:248)、[app.js](D:/Hanako/灵枢/src/js/app.js:252)
蓝队修复：把按钮拆成“复制使用说明”和“导出平台格式”。第一版至少支持通用 Prompt 文本、Hanako/Codex `SKILL.md` 草稿、ChatGPT 自定义指令格式三种之一，否则不要说“导入”。

3. **搜索和问答推荐会被真实用户打穿**
红队攻击：搜索是关键词 + 简单模糊匹配，问答推荐还加入 `Math.random()`，同样回答可能给不同结果。用户搜“我想卖课”“论文降重”“做简历”“AI客服”时，很可能匹配不到或乱匹配。
证据：[小白对接文档.md](D:/Hanako/灵枢/小白对接文档.md:232)、[app.js](D:/Hanako/灵枢/src/js/app.js:315)、[app.js](D:/Hanako/灵枢/src/js/app.js:484)
蓝队修复：先不用上语义搜索，先做可解释的规则分数：意图、场景、输出类型、难度、关键词同义词表。去掉随机分，结果页显示“为什么推荐它”。

4. **数据质量不足以支撑“30 个高质量 Skill”**
红队攻击：现在 30 条更像“示例卡片”，不是可验证 Skill。缺少作者、来源、版本、适配平台、完整提示词、限制条件、真实导入步骤。很多示例输出也偏演示，不代表用户实际复制后能稳定得到结果。
证据：[skills.js](D:/Hanako/灵枢/src/data/skills.js:1)、[产品蓝图](D:/Hanako/灵枢网站产品蓝图1.0.md:619)
蓝队修复：给每条 Skill 加最低验收标准：完整 Prompt、适配平台、3 个测试输入、预期输出、风险说明、维护人、版本号。少收录也可以，但每条必须真的可用。

5. **安全与审核机制目前只在文档里**
红队攻击：蓝图要求识别安全风险、发布审核，但实现没有恶意内容扫描、来源检查、版权检查、敏感数据提醒。更大的隐患是未来如果把外部投稿直接写进 `skills.js`，现有大量 `innerHTML` 渲染会变成 XSS 风险。
证据：[产品蓝图](D:/Hanako/灵枢网站产品蓝图1.0.md:291)、[小白对接文档.md](D:/Hanako/灵枢/小白对接文档.md:233)、[app.js](D:/Hanako/灵枢/src/js/app.js:202)
蓝队修复：短期所有投稿只进“待审核草稿”。渲染用户可控字段时默认转义。风险标签至少包括：隐私、版权、金融/医疗/法律、高风险自动化、外部脚本。

6. **维护成本会在 100+ Skill 时暴涨**
红队攻击：文档说下一步扩到 100+，但数据硬编码在一个 JS 文件里，交互全在一个 `app.js`，没有校验脚本、没有 schema 检查、没有重复 ID 检查、没有内容完整性检查。靠人工编辑会很快乱。
证据：[小白对接文档.md](D:/Hanako/灵枢/小白对接文档.md:62)、[小白对接文档.md](D:/Hanako/灵枢/小白对接文档.md:230)
蓝队修复：保持零框架可以，但需要内容治理：JSON schema、数据校验、唯一 ID 检查、必填字段检查、风险字段检查、预览构建检查。先治理数据，再扩库。

7. **部署说明对小白仍然有门槛**
红队攻击：README 说双击 exe，本地 8080；部署指南说 Netlify Drop、GitHub Pages；小白对接文档又说推送 main 自动部署。对非开发者来说，“到底改哪个目录、推哪里、线上多久更新、失败怎么看”不够明确。
证据：[README.md](D:/Hanako/灵枢/README.md:11)、[部署指南.md](D:/Hanako/灵枢/部署指南.md:3)、[小白对接文档.md](D:/Hanako/灵枢/小白对接文档.md:96)
蓝队修复：分成三条固定路径：普通体验者只打开网站；维护者只改 `src/data/skills.js`；发布者只提交草稿。不要把 Netlify、GitHub Pages、exe 打包混在同一层说明。

8. **本地 exe 的“仅本机访问”表述不严谨**
红队攻击：文档写 exe 仅本机能访问，但 server 绑定的是 `("", PORT)`，通常意味着监听所有网卡。虽然只是静态文件，风险不算高，但和文档承诺不一致。
证据：[部署指南.md](D:/Hanako/灵枢/部署指南.md:12)、[server.py](D:/Hanako/灵枢/server.py:52)
蓝队修复：要么改为只监听 `127.0.0.1`，要么文档说明“局域网内可能可访问”。安全产品感来自这种小地方的诚实。

**优先修复顺序**

1. 先修文案承诺：把“AI 自动整理 / 发布成功 / 一键导入 / 下载 Skill”改成真实能力边界。
2. 再修导入闭环：至少产出一份真正可复制使用的完整 Skill 文本。
3. 然后修发布闭环：投稿进入草稿或 Issue，不要假发布。
4. 最后再扩库和做语义搜索。

一句话红队结论：现在的灵枢最危险的不是技术不够，而是“演示态功能被包装成产品态功能”。蓝队要做的第一刀不是加功能，是把每个按钮背后的结果变成真实、可验证、可解释。
