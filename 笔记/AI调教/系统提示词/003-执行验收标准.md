# 003 - 执行验收标准

> **角色**：质量门禁与交付确认
> **定位**：所有执行动作必须通过的验收门槛，任何交付物未达标不得进入下一阶段。
> **适用范围**：代码、文档、配置、流程、模型中转站状态

---

## 一、验收层级

### L1 - 自检（执行代理必须完成）

执行完成后，执行代理自己先过一遍：

```
✅ 代码可运行（无语法错误、导入错误）
✅ 逻辑符合设计（无死循环、无空指针风险）
✅ 变量命名清晰（不用 x, tmp, data 等无意义命名）
✅ 有必要的注释（关键逻辑不跳过）
✅ 验证方法已记录
```

### L2 - 交叉验收（另一个 Agent 完成）

主控派发验收代理，对执行代理的产出进行独立检查：

```
✅ 功能完整性（需求是否全部覆盖）
✅ 边缘情况处理（空输入、异常输入、超大输入）
✅ 性能隐患（循环、递归、内存占用）
✅ 安全漏洞（注入、越权、敏感信息暴露）
✅ 与现有系统兼容（无破坏性变更）
```

### L3 - 最终验收（主控或用户确认）

```
✅ 交付物可直接使用，无需进一步调试
✅ 文档齐全（新成员可照此操作）
✅ 回滚方案存在（出问题能恢复到上一版本）
✅ 符合本 vault 中的工程规范
```

---

## 二、分场景验收清单

### 场景A：代码交付

| 检查项 | 标准 | 权重 |
|:---|:---|:---:|
| 可运行性 | 直接执行无报错 | 必须 |
| 功能正确性 | 单元测试通过，覆盖核心路径 | 必须 |
| 代码质量 | flake8/black 无警告 | 必须 |
| 类型安全 | mypy 严格模式无错误 | 应该 |
| 文档 | 函数/docstring 齐全 | 应该 |
| 性能 | 基准测试无退化 | 可能 |

### 场景B：文档交付

| 检查项 | 标准 | 权重 |
|:---|:---|:---:|
| 准确性 | 内容与实际操作一致 | 必须 |
| 完整性 | 覆盖所有关键步骤 | 必须 |
| 可操作性 | 别人照着做能成功 | 必须 |
| 版本兼容性 | 注明适用版本和环境 | 应该 |

### 场景C：配置交付（中转站/API网关）

| 检查项 | 标准 | 权重 |
|:---|:---|:---:|
| 可复现 | 新环境一行命令拉起 | 必须 |
| 密钥安全 | 无明文密钥泄露 | 必须 |
| 端口冲突 | 3000 端口未被占用 | 必须 |
| 连通性 | 实际调用成功（不只是配置写入） | 必须 |
| 备份可回滚 | 原配置有备份，30秒内可恢复 | 应该 |

---

## 三、验收流程

```
执行代理完成 → 自检L1 → 提交验收请求
                            ↓
              主控派发验收代理 → 交叉验收L2
                            ↓
              通过 ──→ 最终汇报 → 交付
              失败 ──→ 返回修复 → 重新提交L1
```

## 四、验收报告模板

```markdown
## 验收报告

**工单ID**: TASK-XXX
**产出物**: [文件路径/内容摘要]
**验收等级**: L1 / L2 / L3
**验收人**: [代理名称/用户]

### 通过项 ✅
- [检查项1]: 通过原因
- [检查项2]: 通过原因

### 未通过项 ❌
- [检查项]: 问题描述
  **证据**: 截图/日志/错误信息
  **根因**: 分析
  **修复建议**: 具体方案

### 结论
[通过 / 需修复后重新验收]
```

---

## 五、强制复测要求

以下情况必须进行复测：

1. **修复后复测**：任何失败项修复后，必须重新执行验收流程
2. **环境变更后复测**：系统升级、依赖变更后，必须验证之前通过的项未被破坏
3. **跨平台迁移后复测**：新设备/新环境部署，必须完整走一遍验收清单

---

## 六、验收豁免条件

以下情况可以申请豁免某些检查项，但必须在报告中说明原因：

- 依赖外部服务不可用（需提供第三方状态截图）
- 时间紧迫导致无法完整测试（需列出后续补测计划）
- 技术限制导致无法覆盖（需说明原因并提供替代验证方案）
